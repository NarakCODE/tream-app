# M05 — Teams and workflow configuration

M05 mounts team management, scoped team membership, workflow status catalogs and cycle settings. It extends the authentication, workspace authorization and transactional command infrastructure in [M01–M04](./M01-M04.md). Project, issue and cycle business APIs remain deferred to M06–M08; configuring cycles does not create or roll over cycles.

## Mounted APIs

All paths below start with `/api/v1/workspaces/:workspaceId/teams`. Every request requires a persisted authenticated session. Every mutation, including DELETE, requires a UUID `Idempotency-Key`. Commands reauthorize the current membership before replaying a cached response.

| Method | Relative path                         | Behavior                                                                        |
| ------ | ------------------------------------- | ------------------------------------------------------------------------------- |
| GET    | `/`                                   | List visible active teams with cursor pagination and visibility-filtered totals |
| POST   | `/`                                   | Create team, creator ADMIN membership and six workflow statuses atomically      |
| GET    | `/:teamId`                            | Read a visible team, including a retired team                                   |
| PATCH  | `/:teamId`                            | Update name, description and visibility; key is immutable                       |
| DELETE | `/:teamId`                            | Retire a team after dependency checks; preserve identity/history                |
| GET    | `/:teamId/members`                    | List scoped team memberships                                                    |
| POST   | `/:teamId/members`                    | Add an active workspace membership as MEMBER or ADMIN                           |
| PATCH  | `/:teamId/members/:membershipId`      | Change team role                                                                |
| DELETE | `/:teamId/members/:membershipId`      | Remove team membership without orphaning administration                         |
| GET    | `/:teamId/settings`                   | Read cycle configuration                                                        |
| PATCH  | `/:teamId/settings`                   | Validate and update timezone and cycle settings                                 |
| GET    | `/:teamId/statuses`                   | List active workflow statuses in position order                                 |
| POST   | `/:teamId/statuses`                   | Create a status at an optional insertion position                               |
| POST   | `/:teamId/statuses/reorder`           | Reorder the complete active catalog using `statusIds`                           |
| PATCH  | `/:teamId/statuses/:statusId`         | Update status name/category                                                     |
| POST   | `/:teamId/statuses/:statusId/default` | Replace the usable default under a team lock                                    |
| DELETE | `/:teamId/statuses/:statusId`         | Retire a status; accept `replacementStatusId` when replacement is required      |

Create accepts `name`, `key`, optional `description` and optional `visibility` (`WORKSPACE`, the default, or `PRIVATE`). Keys match `^[A-Z][A-Z0-9]{1,9}$`: 2–10 uppercase letters/digits beginning with a letter. Update does not accept a key change.

Creation seeds Backlog/BACKLOG, Todo/UNSTARTED (default), In Progress/STARTED, Done/COMPLETED, Canceled/CANCELED and Duplicate/DUPLICATE. Active status names are unique after trimming and case normalization. A category change is rejected while the status is referenced by an issue. Default statuses must be BACKLOG or UNSTARTED. Status retirement requires an explicit active same-team replacement when the status is the default or is referenced by any issue, including soft-deleted history. Replacement updates those references transactionally and emits `issue.status_changed` facts.

Cycle settings accept `timezone` (validated by the runtime timezone database), `cyclesEnabled`, `cycleDurationWeeks` (1–8), `cycleStartDay` (0–6), `cycleCooldownDays` (0–14 and strictly shorter than the duration) and `upcomingCyclesCount` (1–10). Field names in HTTP DTOs are camelCase; versioned event payloads use snake_case.

## Authorization and privacy decision

Active workspace membership and workspace lifecycle are checked before team authorization. Workspace OWNER/ADMIN can create teams. Reading a private team requires explicit team membership, including for workspace OWNER/ADMIN. A workspace role does not silently reveal private teams.

| Actor         | WORKSPACE team reads              | PRIVATE team reads                | Existing-team administration   |
| ------------- | --------------------------------- | --------------------------------- | ------------------------------ |
| OWNER / ADMIN | Allowed                           | Explicit team membership required | Allowed after visibility check |
| MEMBER        | Allowed                           | Explicit team membership required | Requires team ADMIN role       |
| GUEST         | Explicit team membership required | Explicit team membership required | Denied, including when shared  |

Team membership is the explicit sharing boundary for this slice. It grants no project/issue sharing behavior for future APIs. Team ADMIN is a scoped capability and never changes the workspace role. Guests can be shared team MEMBERs and remain read-only; they cannot be promoted to team ADMIN. SUSPENDED/LEFT workspace memberships grant no access.

Missing, cross-workspace and unshared private teams return 404. Visible resources with a denied administrative action return 403. List rows, cursors and totals use the same visibility filter. Archived/deleted workspaces cannot receive product commands; retired teams cannot receive ordinary mutations or new issue-number allocations.

This implementation deliberately follows the current separate `modules/teams` boundary and M04 non-enumerating 404 behavior. The older [ADR 0001](../../../docs/adr/0001-work-management-bounded-context.md) proposed a combined `modules/work-management` boundary and non-disclosing 403 responses. Those two details are superseded for this implemented slice by the fresh module scaffolds and this documented HTTP policy. Its CRM Task versus product Issue separation still applies.

## Transactional invariants and migration policy

Application commands lock workspace, then team, then affected statuses. Mutation, idempotent response, validated domain events and audit facts commit together. PostgreSQL constraints provide a second boundary for other writers.

- Team IDs, workspace ownership and canonical keys are immutable. `(workspace_id, key)` is permanently unique, including retired teams. Hard deletion of teams is rejected, preserving key reservations.
- Every active team has exactly one active BACKLOG/UNSTARTED default. Partial unique indexes and deferred commit-time checks prevent concurrent replacement from leaving zero or multiple defaults.
- An active team in an active workspace requires an active non-guest team ADMIN. Team/member changes and workspace membership downgrades/removals cannot leave it without one. Archive/restore uses the same checks when the workspace becomes active again.
- Composite foreign keys bind team membership to the same workspace and issue status to the same team. Active issues require an active team and active status.
- Team retirement is blocked by undeleted nonterminal issues, undeleted linked projects or unfinished cycles. Terminal issue history remains attached. There is no team restore or hard-purge endpoint in M05.
- The internal `TeamIssueNumberAllocator.allocate(tx, userId, workspaceId, teamId)` reserves the next number under the team lock and returns number, identifier and default status. Counter changes roll back with the owning transaction and cannot regress. M07 must call it inside the issue-creation transaction; M05 exposes no allocation API and does not yet implement issue creation/transfers.

[0011_teams_workflows.sql](../src/database/migrations/0011_teams_workflows.sql) adds visibility, tenant-aware memberships, team roles, status retirement and partial unique indexes. [0012_team_invariants.sql](../src/database/migrations/0012_team_invariants.sql) installs immutable identity, usable-team, administration, issue-reference and retirement guards. Retained migrations 0000–0010 are preserved.

For retained data, 0011 backfills membership workspace IDs, preserves an existing usable default where possible, selects/seeds a usable default when required, raises the counter above retained issue numbers and establishes the first active workspace owner as team ADMIN. Existing teams become WORKSPACE-visible; review that upgrade policy before applying it to production data.

Migration refuses reused historical keys and noncanonical keys instead of silently renaming identifiers. Case-normalized duplicate active status names and invalid tenant/cycle data must also be reconciled before the new constraints can succeed. Resolve these conflicts explicitly with an approved data migration; do not edit previously applied migration files or release a reserved key. Migration application is an explicit deployment step, never an application-startup side effect.

M05 adds schema-version-1 contracts for team membership/settings and status catalog changes, alongside existing team created/updated/retired contracts. Runtime and documented catalogs must stay synchronized. [Event contracts](../../../docs/database/event-contracts.md) describe the envelope and compatibility policy.

## Local verification and remaining gates

Run from the repository root with local Docker PostgreSQL available:

```sh
pnpm local:setup
pnpm --filter server check-types
pnpm --filter server lint
pnpm --filter server test
pnpm --filter server test:e2e
pnpm --filter server test:integration:local
pnpm --filter server build
```

The integration harness creates disposable databases and applies retained migrations. Coverage targets real HTTP authorization/privacy, idempotency, concurrent default replacement, status replacement, retirement dependencies, immutable keys and transactional number allocation. Retained-upgrade tests preserve existing identifiers/defaults while backfilling membership tenancy/counters, and reject historically reused keys without a partial upgrade. Use credentials with temporary database creation privileges for the harness, separate from the application's restricted runtime role.

Implementation checkboxes in the [roadmap](../../../docs/roadmap/BACKEND_MILESTONES.md) do not certify production readiness. Production role provisioning, representative retained-data upgrades, full cross-feature RBAC regression, staging/load qualification and recovery rehearsals remain release gates. Future project, issue and cycle APIs must extend the same lifecycle and tenant rules when mounted.
