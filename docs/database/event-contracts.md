# Versioned event contracts

These are **proposed target contracts**, not validators already installed in the NestJS runtime. Server feature producers and consumers were removed by the scaffold reset; retained database history still requires the legacy rollout below. [catalog.json](./events/catalog.json) registers 42 exact `(event_type, schema_version)` pairs; [event-v1.schema.json](./events/event-v1.schema.json) validates their envelopes and concrete payloads using JSON Schema Draft 2020-12. All payloads and envelopes reject unknown properties. Every schema reference is local to that file; its `.example` `$id` identifies the artifact and is not a hosted endpoint.

## Envelope and storage

Every event requires `id`, `workspace_id`, `event_type`, `schema_version`, `occurred_at`, nullable `actor_membership_id`, `aggregate_type`, `aggregate_id`, positive `aggregate_version`, and `payload`. `correlation_id` is optional. Machine/scheduler events use a null actor. An aggregate version is its monotonic committed revision, not its payload schema version. Several facts from the same aggregate revision may share an aggregate version; consumers deduplicate by event ID rather than `(aggregate_id, aggregate_version)`.

The proposed DBML stores `schema_version`, aggregate metadata and correlation metadata on `events`; `events.actor_id` maps to envelope `actor_membership_id`. Persist the business mutation and validated event together. Create an `event_aggregate_heads` row at revision zero, lock it with `FOR UPDATE` before changing the aggregate, and increment once per committed revision in the mutation transaction. The event insert guard requires the current head revision; later events retain their historical revision. Several facts can share that revision and command correlation key. Use the established lock order and retry the whole transaction on serialization/deadlock errors. Preserve event IDs, occurrence times, payloads and revisions during replay; consumers must never regenerate or reinterpret old facts with a newer schema.

`declared-runtime` in the catalog means the event name appears in the current server's event-type registry, **not** that the current producer emits this payload or even emits that event. `proposed` names cover issue transfer/archive/restore and collaboration additions. Historical `agent.run.*` names are excluded. Any event name absent from the catalog has no versioned contract here.

## Payload semantics

Core contracts retain identifiers and operational facts needed by consumers: creation reserves an issue identifier, transfer records both identifiers/teams plus the destination status and cleared/reassigned project/cycle, status and assignment changes record previous and new targets, and cycle completion records the next cycle and exact rollover issue IDs. `issue.deleted` means recoverable soft deletion; `issue.archived` means intentional removal from active planning. Restoring a deleted issue records `restored_at`; it does not implicitly unarchive it. Project completion/cancellation and team retirement remain lifecycle transitions.

Update events contain an explicit `changed_fields` allowlist instead of arbitrary object snapshots. Team restoration uses `team.updated` with `retired_at` in that list. Optional CRM/Dynamic Data/email contracts intentionally contain IDs and minimal stage/provider metadata. They omit record values, email bodies, address lists, OAuth tokens, credentials and other secrets. Collaboration payloads identify resources; authorized consumers fetch current content when appropriate rather than assuming permission from possession of an event.

Schema validation checks structure, enums and timestamps. Producer transactions must additionally enforce tenant membership, `aggregate_id` matching the payload's primary resource ID, timestamp/window ordering, actual before/after state, monotonic aggregate revisions and `rolled_over_count === rollover_issue_ids.length`. A null next cycle requires an empty rollover list. These cross-field/business rules are not guaranteed by JSON Schema alone.

## Compatibility and rollout

1. Dispatch and validate using the pair `(event_type, schema_version)`; validate the complete envelope. Unknown names/versions go to a quarantined failure queue with a visible reason, not a fallback schema. Deploy consumer support before a producer begins emitting a new version.
2. Treat published schemas as immutable. Because validators reject unknown fields, **every wire-contract change, including an additive optional field, gets a new version**. Documentation-only corrections do not. Keep older schemas available for retained events, retries and replay. A new event name starts at version 1.
3. Before the scaffold reset, the removed `StoredEvent` contract used camelCase metadata, an arbitrary payload and no schema version, actor membership, aggregate revision or correlation envelope. Introduce storage columns and producer adapters before enforcing these contracts. Convert `actorUserId` through the workspace membership relationship; never treat a global user ID as a membership ID. Existing camelCase payloads must be explicitly mapped rather than silently labeled version 1.
4. Inventory actual retained payloads, classify legacy records, and backfill only events whose metadata/facts can be reconstructed reliably. Keep an explicit legacy path for the remainder or quarantine them; do not fabricate aggregate revisions, identifier history or rollover issue IDs. Preserve original legacy bytes and provenance. Run dual validation/reporting and consumer compatibility checks before switching producers, then enable enforcement.
5. Event delivery is at least once. Use `event_consumer_receipts` atomically with same-database side effects; external providers need an event-derived idempotency key or reconciliation; replay must preserve the original schema and facts. Keep historical events immutable through archive/delete transitions. Apply the separate retention/erasure policy to sensitive content, never place secrets in event payloads, and redact quarantine logs.

## Executable examples

[fixtures](./events/fixtures) contains valid issue creation and cycle completion events, plus rejected missing-identifier, negative-rollover-count, unsupported-version and leaked-email-token examples. Validate with Ajv 8's `dist/2020` entry point and `ajv-formats` (`strict: true`, `allErrors: true`); load the schema as a local JSON object, with no network resolution. The catalog payload pointers are file-relative JSON Pointers for tools inspecting individual contracts. Consumer validation should use the complete envelope so the discriminator and aggregate type are checked together.
