# M06 — Projects and milestones

M06 extends [teams and workflows](./M05.md) with workspace project-status catalogs, projects, scoped members and team associations, milestones, health updates and computed progress. Issue creation and transfers remain M07; project progress reads retained issue assignments without exposing an issue-write API.

## Mounted APIs

All routes require persisted authentication and start with `/api/v1/workspaces/:workspaceId`. The status catalog is workspace-scoped; project child resources inherit the full project visibility check.

| Method               | Relative path                                  | Behavior                                                |
| -------------------- | ---------------------------------------------- | ------------------------------------------------------- |
| GET / POST           | `/project-statuses`                            | List active catalog / create status                     |
| PATCH / DELETE       | `/project-statuses/:statusId`                  | Update / retire with optional `replacementStatusId`     |
| POST                 | `/project-statuses/reorder`                    | Reorder all active statuses using `statusIds`           |
| POST                 | `/project-statuses/:statusId/default`          | Replace usable default                                  |
| GET / POST           | `/projects`                                    | List visible active projects / create project           |
| GET / PATCH / DELETE | `/projects/:projectId`                         | Read / update / soft-delete project                     |
| POST                 | `/projects/:projectId/archive`                 | Archive after unfinished-work checks                    |
| POST                 | `/projects/:projectId/restore`                 | Restore archived or deleted project                     |
| GET / POST           | `/projects/:projectId/teams`                   | List / add team association                             |
| DELETE               | `/projects/:projectId/teams/:teamId`           | Remove unused association while retaining a usable team |
| GET / POST           | `/projects/:projectId/members`                 | List / add scoped project member                        |
| DELETE               | `/projects/:projectId/members/:membershipId`   | Remove project membership                               |
| GET                  | `/projects/:projectId/progress`                | Compute issue progress                                  |
| GET / POST           | `/projects/:projectId/milestones`              | List / create milestones                                |
| PATCH / DELETE       | `/projects/:projectId/milestones/:milestoneId` | Update / delete unreferenced milestone                  |
| POST                 | `/projects/:projectId/milestones/reorder`      | Reorder all milestones using `milestoneIds`             |
| GET / POST           | `/projects/:projectId/updates`                 | List update history / publish health update             |

Creation requires `name` and a nonempty unique `teamIds` array. Optional fields are `summary`, `description`, `statusId`, `priority`, `leadId`, `startDate` and `targetDate`. The creator becomes a project member atomically. Project catalog categories are PLANNED, STARTED, PAUSED, COMPLETED and CANCELED; creation defaults to PLANNED. Select a completed/canceled `statusId` through PATCH to perform those lifecycle transitions. Catalog defaults must be PLANNED. Health updates accept `body` and `health` (`ON_TRACK`, `AT_RISK`, `OFF_TRACK`) and preserve the scoped author.

## Authorization and privacy

Every project read checks active workspace membership and visibility of **every linked team**. Workspace OWNER/ADMIN and project membership do not bypass a private team's explicit sharing requirement. Guests cannot access projects until a typed project-sharing policy is implemented. Missing, foreign-workspace and hidden projects return 404; a visible project with a denied management action returns 403.

After visibility checks, workspace OWNER/ADMIN, the project lead, explicit project members or a caller who administers every linked team can manage the project. Creating projects requires workspace OWNER/ADMIN or administration of every selected team; catalog administration remains workspace OWNER/ADMIN. Adding a project member grants scoped management, so select membership intentionally.

Lists, totals, cursors, progress, members, milestones and update history use the same project visibility policy. A private-team association cannot be inferred through an aggregate count or a child-resource endpoint. Application commands reauthorize the caller before replaying an idempotent response.

## Lifecycle and transactional guarantees

Every mutation requires a UUID `Idempotency-Key`. State changes, validated versioned events, audit facts and the replayable response commit together. Workspace, project and sorted team locks serialize conflicting changes; PostgreSQL constraints enforce tenant and lifecycle invariants for other writers.

- An undeleted project has at least one usable team at transaction commit. Team associations must belong to the project's workspace.
- Removing an associated team is blocked while retained issues depend on that association. M06 does not silently detach or transfer those issues.
- Status catalogs have exactly one usable default; active names and positions remain unique. In-use status retirement requires explicit replacement.
- HTTP start and target dates are date-only values with a valid chronological range. Existing project timestamp columns are retained; new inputs are stored at UTC midnight. Milestone dates use a date-only column. Leads, project members and update authors refer to scoped workspace memberships.
- Milestone assignments belong to the issue's project. Milestone ordering is explicit. Project progress counts undeleted issues by completed, canceled, duplicate and unfinished categories; `percentComplete` is completed / total × 100, rounded to two decimals, or zero when no work exists. It is computed rather than persisted as an authoritative percentage.
- Completion, cancellation, archive and deletion preserve linked issue statuses and return 409 while any undeleted linked issue is unfinished; no unrelated issue status is silently rewritten.
- Restore revalidates the project's usable teams, catalog status, lead and every project membership. New assignments cannot target a project that is ineligible for active work; historical issue links remain inspectable.

## Retained-schema migration policy

Retained migrations 0000–0012 remain unchanged. M06 reconciles the legacy project enum with workspace-scoped catalog references and backfills project-team tenancy. Unknown legacy creators remain null; new projects record the authenticated creator as a scoped membership. Existing project timestamp values remain unchanged; new date-only project inputs are stored at UTC midnight. Milestone dates use a date-only column. Catalogs are seeded transactionally on workspace creation, rather than by a GET side effect. Retained COMPLETED projects receive a missing completion timestamp derived from `updated_at`; that reconciliation value is not evidence of the actual historical completion time. Deployment operators must review these interpretations for retained data.

Migration does not manufacture cross-workspace relationships or silently discard issue history. Invalid legacy relationships must be reconciled explicitly before commit-time constraints are enabled. The [0013 schema upgrade](../src/database/migrations/0013_projects_workflows.sql) and [0014 invariant guards](../src/database/migrations/0014_project_invariants.sql) reject undeleted legacy projects lacking an explicit usable team and closed projects containing unfinished work. Review the incremental migration SQL against representative retained data before production rollout. The proposed [target ERD](../../../docs/database/linear-workspace.dbml) remains broader than the implemented retained schema.

## Verification and release gates

Run from the repository root with local Docker PostgreSQL available:

```sh
pnpm --filter server check-types
pnpm --filter server lint
pnpm --filter server test
pnpm --filter server test:e2e
pnpm --filter server test:integration:local
pnpm --filter server build
```

The PostgreSQL harness uses disposable databases and retained migrations. M06 validation passed 15 HTTP/invariant cases and four retained-upgrade cases; the complete PostgreSQL suite passed 60 tests across seven suites. The e2e suite passed 16 tests. Production role provisioning, representative migration rehearsals, cross-feature RBAC regression, load qualification and recovery gates remain pending.
