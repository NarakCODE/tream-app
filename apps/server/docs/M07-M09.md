# M07–M09 — Issues, cycles and collaboration

These milestones extend [M06 projects](./M06.md). Product Issues remain separate from CRM Tasks. Private files and uploads are implemented in [M10](./M10.md); notifications and external integrations are later milestones.

## API groups

Every route requires a persisted authenticated session. Mutations require a UUID `Idempotency-Key`; changes to an existing issue, cycle, comment, label or template also require the relevant `expectedRevision` in the request body. Read responses and committed mutation responses expose `revision`. A stale revision returns 409; reusing the same command identity and payload returns the original result only after current authorization is checked again.

## Issue and transfer guarantees

Issue creation reserves a team number and identifier in the same transaction as the issue, events, audit and idempotent response. Lookup through `/api/v1/workspaces/:workspaceId/issues/identifier/:identifier` continues to resolve old aliases after transfer, archive and trash, subject to current access. Alias rows remain permanently reserved; physical deletion and reassignment are rejected.

New assignments validate active, tenant-scoped teams, statuses, non-guest assignees, projects, milestones and enabled usable cycles. A milestone belongs to the assigned project, a cycle belongs to the issue's team, and a project's team association must permit the issue. Ordinary edits can retain historical references; restoration and transfer revalidate dependencies.

Transfers preserve the internal issue ID, reserve a fresh destination identifier and retain every previous alias. An explicit destination status is validated against the destination team; otherwise the command chooses the first active status in the source category, falling back to the destination default. Cycle/project/milestone links are cleared unless explicitly remapped. Workspace labels and compatible destination-team labels survive; incompatible team labels are removed with facts in the same transaction. No SLA capability is currently enabled.

Parent and relation changes serialize on the workspace. Parent cycles and directed BLOCKS/DUPLICATES cycles are rejected, including competing commands. RELATED edges use canonical undirected ordering. Private ancestor teams and linked projects are checked before issue reads, list totals, cursors and identifier lookup. Relation output omits inaccessible peers. Guest writes are denied; explicit team sharing permits only issue reads whose full dependencies are also visible.

## Cycles and scheduling

Cycle windows are half-open `[startsAt, endsAt)` and PostgreSQL exclusion constraints reject overlaps while allowing adjacent windows. Calendar planning uses the team's IANA timezone and cycle settings; invalid local times and calendar inputs are rejected. Raw UTC window APIs remain explicit about offsets.

Manual and scheduled completion share one transactional implementation. Only undeleted, unarchived UNSTARTED/STARTED issues move to the valid next cycle; BACKLOG, COMPLETED, CANCELED and DUPLICATE issues remain attached. Each moved issue advances its revision and emits a cycle-change fact. Source completion, the stable next-cycle result, rollover history, events and audit commit together. Rollover history remains valid if an issue later transfers teams.

When background workers are enabled, a bounded scheduler sweep handles due work and maintains upcoming cycle plans for enabled teams. Failed commands roll back and expose generic scheduler error metadata for retry; operational error metadata does not change the cycle's business revision. Completion responses omit private issue IDs/counts; reports compute counts from currently authorized issue data. Tests disable automatic timers and exercise the same scheduler path directly.

## Collaboration and privacy

Comments have one typed issue, project or project-update target; replies retain that target and historical author membership. Authors can edit their own content while active, and visible-resource administrators can moderate trash/restore. Revisions prevent concurrent comment edits from silently overwriting one another. Reactions and subscriptions use unique resource/member keys; guests cannot write them.

Workspace and team labels have normalized active-name uniqueness. Scope edits are blocked while assignments exist; projects accept workspace labels. Issue label changes participate in the issue revision contract, and transfer/link races cannot retain incompatible labels. Archived labels do not accept new assignments.

Templates validate a fixed defaults grammar and all referenced tenant resources. Team-scoped templates can reference matching team statuses/cycles and compatible planning resources; workspace templates avoid team-specific defaults. Lists omit defaults, while detail and instantiation revalidate referenced resource access. Template instantiation creates the issue and label assignments in one transaction. Issue activity reads authoritative issue facts and omits payload bodies/references from its public projection.

`issue.updated` uses schema version 2 to add ordering fields while preserving its original version 1 contract. Typed planning comments use schema version 2 for `comment.created`, `comment.updated` and `comment.deleted`. Published issue-comment version 1 contracts remain valid. Newly introduced event families use their registered version 1 shapes; notification delivery is M13.

## Database rollout and verification

Migrations 0015–0019 add resource revisions, issue aliases/relations, cycle tenant links/history, collaboration tables, tenant keys and guards. Retained migrations 0000–0014 are unchanged. Existing current identifiers, issue/cycle identity, issue associations and historical facts are preserved. The upgrade rejects malformed identifiers, foreign legacy cycle links and overlapping retained windows instead of silently rewriting them. Apply reviewed migrations explicitly with `pnpm --filter server db:migrate`; startup never migrates the database.

The [revision and identifier ADR](../../../docs/adr/0002-resource-revisions-and-identifier-reservations.md) records the concurrency contract. Run `pnpm --filter server lint`, `check-types`, `test`, `test:e2e`, `test:integration:local` and `build`. PostgreSQL integration suites create disposable databases, test retained upgrades and verify authorization, concurrency and rollback. Production qualification, staging and recovery rehearsals remain M16–M18.

Implementation verification passed with 303 unit tests, 110 PostgreSQL integration tests, 17 application e2e tests, lint, typecheck and build. Migrations 0015–0019 were applied to the local development database. The 180-request Postman collection passed static schema/script/body/variable checks; the new manual recipes were not run through Postman/Newman.
